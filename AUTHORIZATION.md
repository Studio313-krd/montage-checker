# Авторизация и роли

## Первый OWNER

При первом запуске на пустой базе Server создаёт `OWNER` из переменных:

- `OWNER_LOGIN`;
- `OWNER_PASSWORD`;
- `OWNER_DISPLAY_NAME`.

Пароль должен содержать 12–200 символов, заглавную и строчную буквы, цифру и специальный символ. В PostgreSQL сохраняется только versioned PBKDF2 hash ASP.NET Core Identity (210 000 итераций). После успешного первого входа очистите `OWNER_PASSWORD` в Portainer и redeploy stack: уже созданный OWNER не изменится.

## Сеанс

`POST /api/auth/login` возвращает access JWT на 15 минут. Refresh token на 30 дней передаётся только cookie `montage_refresh` с флагами `HttpOnly`, `Secure`, `SameSite=Strict` и путём `/api/auth`; API и React UI работают на одном домене.

Refresh token — 512-битное случайное значение. В базе хранится только его SHA-256 hash. `POST /api/auth/refresh` каждый раз отзывает старый token и выдаёт новый. Повторное использование уже отозванного token считается компрометацией и отзывает все активные refresh tokens пользователя. `POST /api/auth/logout` отзывает текущий token и удаляет cookie.

Для защищённых запросов клиент передаёт:

```http
Authorization: Bearer <access-token>
```

Основные endpoints:

- `POST /api/auth/login` — вход;
- `POST /api/auth/refresh` — ротация refresh token;
- `POST /api/auth/logout` — завершение сеанса;
- `GET /api/auth/me` — текущий пользователь;
- `/api/admin/users` — создание, изменение, деактивация пользователей и назначение сотрудников.

## Роли

| Роль | Доступ |
| --- | --- |
| `OWNER` | Полный доступ, включая создание других OWNER |
| `ADMIN` | Управление системой и пользователями, кроме назначения/изменения OWNER |
| `MANAGER` | Просмотр только назначенных сотрудников; screenshots и reports для них |
| `VIEWER` | Просмотр только назначенных сотрудников |

Для `OWNER` и `ADMIN` список `employeeIds` не задаётся — им доступны все сотрудники. Для `MANAGER` и `VIEWER` он задаётся при создании и обновлении пользователя. Недоступный сотрудник возвращается как `404`, чтобы не раскрывать существование записи.

Нельзя деактивировать себя, изменить собственную роль или удалить последнего активного OWNER. Изменение роли, деактивация и смена пароля отзывают активные refresh tokens. На каждом защищённом запросе Server проверяет, что пользователь активен и роль в JWT по-прежнему актуальна.

## Защита входа и аудит

Login ограничен пятью запросами в минуту на IP без очереди; ответ при превышении — `429`. После пяти неверных паролей учётная запись блокируется на 15 минут. Ответ входа намеренно одинаков для неизвестного логина, неверного пароля, деактивированной и заблокированной записи.

В `audit_logs` записываются успешные/неуспешные входы, logout, refresh/reuse, а также создание, изменение, деактивация пользователя и смена пароля. Пароли и raw tokens в аудит не попадают.

## Доступ Windows Agent

Agent не использует пользовательский JWT. Администратор создаёт для сотрудника одноразовый enrollment token через `POST /api/admin/employees/{employeeId}/agent-enrollment`; endpoint ограничен ролями OWNER/ADMIN и rate limit. После `POST /api/agent/enroll` код помечается использованным, а Agent получает отдельный device credential.

Для последующих запросов Agent передаёт `Authorization: Device <credential>`. В PostgreSQL хранится только SHA-256 hash credential. Server проверяет срок действия, отзыв credential, статус Agent и активность сотрудника; идентификаторы Agent, сотрудника и компьютера в heartbeat обязаны совпадать с credential. Повторная регистрация той же пары «сотрудник + компьютер» сохраняет идентификаторы, отзывает прежние credentials и выдаёт новый.
