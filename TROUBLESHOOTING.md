# Сотрудник работает, но панель показывает «Нет связи»

Запущенный процесс Agent, успешный выбор сотрудника и доставленный heartbeat — разные признаки. Карточка вычисляет Online на Server по `agents.status` и `agents.last_seen_at_utc`. Допустимая пауза составляет три интервала heartbeat, но не меньше 90 секунд. Число часов в карточке — длительность Offline-интервала выбранного компьютера; оно не доказывает, что сотрудник не работал.

Последний скриншот хранится отдельно и продолжает отображаться при Offline. До этого исправления интерфейс показывал только время суток скриншота и heartbeat, поэтому вчерашний снимок мог выглядеть свежим. Теперь рядом со временем указывается дата. Для изменения веб-интерфейса требуется отдельно обновить Server/SPA.

## Проверенные ошибки Agent 0.10.1

1. `AgentRuntime.FlushQueueAsync` безусловно публиковал `Connected` в конце цикла, даже если после ошибки очередь ожидала следующей попытки и ни один heartbeat не был принят. Это также затирало сообщение об отклонённом heartbeat.
2. Ответ HTTP 428 переводил runtime в `OperatorSelectionRequired` и останавливал отправку. Tray повторно проверял локальный срок смены: если он ещё не истёк, окно выбора не открывалось, а завершившийся runtime оставался в поле `_runtime`. Процесс и значок продолжали существовать без отправки heartbeat.
3. Тот же ответ на старое событие очереди мог остановить уже новую смену. После повторного входа возникал риск повторять этот цикл.
4. HTTP-коды и детали ошибок отправки не показывались. Поле `AgentRuntimeStatus.Details` не выводилось в tray, а необработанные ошибки завершали Agent без локального журнала.

Первые два дефекта воспроизведены тремя новыми тестами на исходном коде: временная ошибка, отклонённый heartbeat и отказ текущей смены. Старые 62 теста проходили. В `0.10.2` статус сохраняется до реального результата отправки; отказ текущей смены сначала делает локальный выбор недействительным, а события прошлой смены откладываются и не блокируют текущие. Добавлены проверки heartbeat, скриншотов и безопасных диагностических сообщений.

## Повторное открытие окна входа в 0.10.2

Полученный 11.09.2026 журнал показал один запуск процесса и последовательность `Starting → Connected → OperatorSelectionRequired` с HTTP 428. Это повторный выбор смены после ответа сервера, а не аварийный перезапуск EXE. Успешная отправка части очереди не гарантирует, что сервер примет следующее событие.

В коде обнаружена несовместимость часов: Server задаёт `StartedAtUtc` по своему времени и требует `StartedAtUtc <= heartbeat.TimestampUtc`, а Agent 0.10.2 брал timestamp из Windows. Даже отставание на несколько секунд способно отклонить первый heartbeat после правильного пароля. Точный размер расхождения на рабочем ПК из приведённого журнала не определяется.

Agent 0.10.3 синхронизирует внутренние часы с `StartedAtUtc` успешного входа. Далее время heartbeat, скриншотов и проверки окончания смены измеряется монотонно, без зависимости от перевода часов Windows. При перезапуске время уточняется через `GET /api/agent/operators`; при недоступной сети используется сохранённая поправка. Старые события не переписываются и не присваиваются новой смене. Поправка записывается в журнал строкой `Server clock synchronized; offsetSeconds=...`. При повторном отказе его причина теперь видна и в окне выбора сотрудника.

Установка: в открытом окне нажмите **Я НЕ МОНТАЖЕР**, замените EXE на 0.10.3 в той же папке и запустите. Если окно закрыто, завершите через tray **Выход** с паролем `IDDQD`. Настройки и очередь оставьте на месте. Обновлять Server для исправления времени не требуется.

Проверки: unit-тесты моделируют отставание Windows на 5 и 120 секунд, ошибочную дату, перевод часов во время смены, offline-перезапуск и время первого heartbeat. API integration воспроизводит HTTP 428 для события за пять секунд до начала смены, затем отправляет тот же UUID с серверным временем и проверяет Online в dashboard.

## Проверка инфраструктуры

Проверка исправления: 74 теста .NET, проверка форматирования, frontend lint/build и `Stage13.Integration.ps1` (настоящие PostgreSQL и Server, Agent API и Excel) завершились успешно. Это локальная проверка; изменения не развёрнуты в production.

Причина отказа именно на рабочем ПК требует его статуса/журнала и при необходимости серверных логов. При проверке 11.09.2026 в 07:48 UTC production `/health/ready` ответил HTTP 200 `Healthy`. Это подтверждает доступность сервера и базы в тот момент, но не приём heartbeat конкретного устройства. В этой рабочей среде нет подключения к production PostgreSQL или компьютеру сотрудника.

Сервер проверяет время события внутри подтверждённой смены. Несовпадение часов Windows и Server, закрытая смена или старое событие могут дать HTTP 428. HTTP 400 указывает на валидацию данных; 401/403 — на доступ; 5xx — на серверную ошибку. Определять причину без фактического ответа нельзя.

## Действия на компьютере сотрудника

1. До перезапуска запишите текущий статус, дату последней синхронизации и число событий в очереди. Проверьте, какой сотрудник указан в tray.
2. Для быстрого восстановления на `0.10.1` используйте **Сменить монтажёра…** и повторно выберите сотрудника. Это может восстановить runtime, но при повторном отказе проблема вернётся.
3. Для установки исправления выберите **Выход**, введите `IDDQD`, дождитесь исчезновения значка и замените только EXE файлом `0.10.2` в той же папке. Не удаляйте `%LocalAppData%\MontageMonitor`.
4. Запустите новый EXE. Если появится выбор сотрудника, войдите. Проверьте обновление **Последняя синхронизация** и heartbeat в веб-панели через 30–60 секунд; при большой очереди доставка истории может занять больше времени.
5. Если связь не появилась, откройте **Открыть журнал диагностики…** и проверьте строки после запуска `0.10.2`. При сообщении о расхождении часов включите автоматическую синхронизацию даты и времени Windows, затем повторите выбор сотрудника.

Не пересоздавайте сотрудника или компьютер и не очищайте локальную очередь для устранения индикации: это не устанавливает причину и может потерять ещё не отправленную историю.

## Серверная проверка

В Portainer проверьте запросы `POST /api/agent/heartbeat` в логах reverse proxy и соответствующие ошибки контейнера Server. Сопоставляйте время с журналом Agent. Не публикуйте заголовок `Authorization`, пароли или `agent.json` целиком.

Следующий запрос PostgreSQL только читает состояние компьютеров и их последние события. Он не выбирает credentials или пароли:

```sql
SELECT now() AS server_now_utc,
       c.id AS computer_id, c.name AS computer_name,
       a.id AS agent_id, a.installed_version, a.status, a.last_seen_at_utc,
       c.last_heartbeat_at_utc,
       h.timestamp_utc AS last_event_time_utc,
       h.created_at_utc AS last_event_received_utc,
       e.name AS last_event_employee,
       os.started_at_utc AS operator_started_utc,
       os.expires_at_utc AS operator_expires_utc,
       os.ended_at_utc AS operator_ended_utc
FROM computers c
LEFT JOIN agents a ON a.computer_id = c.id
LEFT JOIN LATERAL (
    SELECT employee_id, timestamp_utc, created_at_utc
    FROM heartbeats WHERE computer_id = c.id
    ORDER BY timestamp_utc DESC, created_at_utc DESC LIMIT 1
) h ON true
LEFT JOIN employees e ON e.id = h.employee_id
LEFT JOIN LATERAL (
    SELECT started_at_utc, expires_at_utc, ended_at_utc
    FROM agent_operator_sessions WHERE agent_id = a.id
    ORDER BY started_at_utc DESC LIMIT 1
) os ON true
WHERE NOT c.is_revoked
ORDER BY c.name;
```

Если дата heartbeat старая, проверяйте доставку Agent и ответы API. Если heartbeat свежий, а карточка Offline, сопоставьте `computer_id` из ответа `/api/dashboard` с этим запросом: у сотрудника может быть несколько ПК, и карточка выбирает один из них. Сравните также время событий и их приёма — это разные поля.
